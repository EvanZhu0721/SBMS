## 最终规则

| 场景 | 最终方案 |
|---|---|
| 两轴均为 1:1 | 原像素直通，不去彩边 |
| 纯放大 | 源图选择性去彩边 → EWA Lanczos4Sharpest 明暗细节＋双线性色度，抗振铃强度 0.8 |
| 任一轴缩小 | 源图选择性去彩边 → 按每轴缩小比例扩展采样范围的 Lanczos3 |

去彩边采用 `dynamic-filter.js` 中 `u_refine=2` 的既定实现：中性边缘证据、RGB/BGR 顺序与相邻色带保护，加上最长 16 个源像素的连通窄笔画追踪。强度保持 0.96，本次不为新截图重新调阈值。运算使用编码 RGB；不增加锐化、线性光转换或整图去饱和。

1:1 保持旁路。没有缩放时，应保留系统已有的文字光栅与真实彩色细节；不能把原生 ClearType 的所有非灰像素都算作需要消除的错误。

放大时，对同一份去彩边后的源图，令 `E = EWA(source)`、`B = bilinear(source)`，输出为 `clamp(Y(E) + B - Y(B), 0, 1)`，其中 `Y` 的 RGB 权重为 `(0.2126, 0.7152, 0.0722)`。保留原 EWA 的明暗细节，颜色部分由相邻四个源像素的非负权重插值得到，不再用负瓣增强颜色。超出 RGB 范围时的截断和 8 位量化仍可能改变亮度；灰度输入则保持原来的 EWA 像素。

这次没有追加文字检测条件，也没有改变去彩边阈值。真实细彩线的颜色过渡会变柔和，这是有意接受的代价，不能把其色度下降也计为“改善”。

这是算法与实验实现的定稿。产品实现仍需独立完成原生 GPU 成本、真实动态桌面与更广泛内容验证。当前演示覆盖每轴最多 3 倍缩小；不是任意比例、HDR、所有子像素排列的验收。

## 当前 SBMS 基线

| 条件 | 当前实现 |
|---|---|
| 两轴同时缩小，且每轴 `1.0001 < 源尺寸 / 输出尺寸 <= 2` | 精确面积平均＋现有选择性彩边抑制 |
| 其他情况 | 双线性 |

测试基线保存于 [sbms-current-baseline.hlsl](../work/sampling-lab/sbms-current-baseline.hlsl)。实验里的 `sbms()` 与当前 HLSL 使用相同门槛、像素中心、面积权重和去彩边公式。演示使用重复边界，产品使用钳位边界，因此只比较远离画布边界的完整文字区域。WebGL 的手工插值与原生 D3D11 硬件采样不保证逐位一致。

## 输入与测量

输入是独立生成的 Win32 GDI 窗口截图：Segoe UI 英文、Microsoft YaHei 中文、Consolas 代码，各有明暗底。ClearType 与灰度抗锯齿分别原生绘制；没有缩放旧截图来生成高 DPI 输入。

各场景按 `源字体 DPI = 100% / 纵向采样倍率` 选择截图，保持约 12 输出像素的 em 高度。240% 的源 em 为 28.8 px，GDI 取整至 29 px，输出为 12.0833 px。单轴缩小仅保持字高，横向压缩仍然存在。放大测试的 50% / 66.667% 是受控字体与布局比例，不代表 Windows 的桌面缩放选项。

每档都比较同一截图的两套输出，覆盖 `(0,0)`、`(1,0)`、`(1,1)` 三个整数源像素位移。统计原生文字的六行完整内区，不用跨 DPI 的字形像素对齐充当真值；不同 DPI 的 hinting 与字宽舍入本来就可能不同。

- 残余色度：逐像素 `max(R,G,B) - min(R,G,B)` 的总和。对预期中性的缩放文字，可衡量彩边变化；它不是综合画质分数。
- 强色差像素：上述通道差至少为 8/255 的像素数。
- 灰度对照：检查采样是否引入颜色，并观察与原始亮度范围相比的越界及字重变化。更多对比度不自动等于更准确。
- 相位：三个位移分别保留结果，避免仅凭一张恰好对齐的截图宣布改善。

## 各比例实测

下表为 ClearType 六行文字的统计：三个位移分别计算相对 SBMS 的变化，再取平均；括号为三次结果的范围。向下箭头表示减少，向上箭头表示增加。百分比只描述指定色度指标，不是“画质提升百分比”。

| 输出 / 源倍率 | 源尺寸 → 输出尺寸 | 源字体比例 | 残余色度总量变化，均值（范围） | 强色差像素数变化，均值 |
|---|---|---:|---:|---:|
| 1:1 | 1920×1080 → 1920×1080 | 100% | 0%，像素不变 | 0% |
| 2× | 1920×1080 → 3840×2160 | 50% | ↓15.84%（15.84–15.84%） | ↓11.34% |
| 1.5× | 2560×1440 → 3840×2160 | 66.667% | ↓24.13%（24.04–24.23%） | ↓16.27% |
| 0.75× | 2560×1440 → 1920×1080 | 133.333% | ↓62.05%（61.71–62.58%） | ↓55.73% |
| 0.5× | 3840×2160 → 1920×1080 | 200% | ↓81.66%（81.54–81.72%） | ↓75.65% |
| ⅓× | 5760×3240 → 1920×1080 | 300% | ↓94.28%（94.22–94.35%） | ↓95.35% |
| 5/12×，6K → 1440p | 6144×3456 → 2560×1440 | 240% | ↓89.96%（89.63–90.41%） | ↓86.24% |
| 仅横向 0.75× | 2560×1440 → 1920×1440 | 100% | ↓48.53%（46.93–49.33%） | ↓34.98% |

0.75× / 0.5× 是对比当前已有的“面积平均＋旧去彩边”，收益不只是替换双线性。⅓× / 5/12× 和单轴缩小在当前 SBMS 中走双线性，最终方案补上了对应尺度的低通采样，减少断笔、锯齿与彩色碎点。更平滑的轮廓也会显得更软，不能用局部对比度越高越好来排序。

上一次 RGB EWA 方案在同一组小字上，色度总量分别增加 28.43% 和 10.18%；新方案修复了这两组样本的净退化。2× 峰值色差由旧方案的 144/255 降至 94/255，SBMS 为 112/255。1.5× 新方案峰值与 SBMS 相同。这不等于没有彩边：2× 的源字只有 6 px em，滤波无法补回未被光栅化的细节。0.75× 也仍有局部例外：总量减少约 62%，单个像素的最大色差增加 0.85%–6.84%；本次没有改变缩小分支。

正常字号和真实图标的前后对照、多个位移及整帧回归另见[放大优化验证](../work/sampling-lab/upscale-verification.json)。独立候选试验见[候选取舍](../work/sampling-lab/probes/upscale-options.md)与[GPU 探针结果](../work/sampling-lab/probes/upscale-chroma.json)；不能以真实图标色度下降多少来评价其质量。

### 放大优化前后

另将 6、8、12、15 px 源字体分别放大 1.5× 和 2×，检查正常字号是否也受益。这里固定源字体，不再要求不同源字体的最终输出字号相同；每次前后对照仍使用同一份截图、同一采样位置。以下为三个源位移的均值，百分比均相对当前 SBMS：

| 源字高 → 输出字高 | 优化前残余色度 | 优化后残余色度 | 峰值色差：SBMS / 优化前 / 优化后 |
|---|---:|---:|---:|
| 6 → 12 px，2× | ↑28.43% | ↓15.84% | 112 / 144 / 94 |
| 8 → 12 px，1.5× | ↑10.18% | ↓24.13% | 125 / 162–171 / 125 |
| 12 → 24 px，2× | ↓31.78% | ↓51.52% | 117 / 196 / 117 |
| 15 → 30 px，2× | ↓54.12% | ↓66.92% | 117 / 200 / 117 |

[真实文字三列对比图](../work/sampling-lab/upscale-exports/text-comparison.png)按输出原像素导出，依次为 SBMS、优化前、优化后。高 PPI 副屏上的正常字号也能出现旧 EWA 增强局部彩边的现象，并不只发生于 6 px 极小源字。

真实图标同时覆盖 16 / 48 px、明暗底和两种放大倍率，另有 256 px 照片。相对优化前，TikTok 的整图色度总量减少 3.88%–14.06%；在优化前色差至少 32/255 的同一像素集合中，减少 6.70%–19.37%。这些数值代表真实彩边变柔的代价，不能记为收益。其余已测图标的整图色度变化幅度不超过 3.05%，照片约 0.093%；不代表所有局部像素变化都很小。

[真实图标三列对比图](../work/sampling-lab/upscale-exports/color-comparison.png)同时展示小尺寸反例。灰度文字与旧 EWA 逐像素一致，彩色内容则因最终 RGB 截断而仍有亮度偏差：已测图标/照片最大为 5.37/255，文字最大为 8.72/255。没有宣称所有像素亮度严格不变。

### 振铃与字重代价

灰度文字在两套算法、所有比例下均未产生色度，但最终方案的负瓣会带来亮暗越界。以下使用共同源位移 `(0,0)`，统计同样六行；“越界”指超出对应源行亮度范围超过 1/255。当前 SBMS 的这项计数和最大越界均为零。

| 倍率 | 最终版越界像素数 | 最大亮度越界 / 255 | 相对背景的绝对亮度差总量变化 |
|---|---:|---:|---:|
| 1:1 | 0 | 0 | 0% |
| 2× | 1,909 | 13 | +5.15% |
| 1.5× | 2,092 | 20 | +6.46% |
| 0.75× | 2,733 | 32 | +11.37% |
| 0.5× | 2,443 | 24 | +9.44% |
| ⅓× | 2,420 | 28 | +7.12% |
| 5/12× | 2,575 | 24 | +11.37% |
| 仅横向 0.75× | 1,435 | 28 | +7.91% |

最后一列反映字重、边缘和光晕合计的变化，不是清晰度得分。明暗底、不同文字的表现也不相同；这是用户先前观察到的“边缘鬼影、背景不干净”需要保留的取舍。放大色度优化保持灰度输出不变，因此没有消除这些明暗振铃。

## 验证范围

[完整数值报告](../work/sampling-lab/sbms-final-verification.json)包含 8 比例 × 2 文字渲染方式 × 3 源位移，共 48 组。7,488 次 CPU / GPU 抽样比较的通道误差均不超过 1/255；同帧分屏逐像素一致。1:1 在四种对照模式中都保持右侧原像素，灰度文字不引入色度。桌面、设置展开及窄屏实际截图已检查。新旧完整流程、历史页及真实图标的回归记录在[放大优化验证](../work/sampling-lab/upscale-verification.json)。

放大专项另覆盖 48 组文字条件、52 组真实图标/照片条件，共 14,556 次 CPU / GPU 抽样，误差均不超过 1/255。24 组灰度文字条件与优化前逐像素一致；12 组 1:1 / 缩小条件的新旧整帧逐字节一致。四种对照切换不改变右侧、源图与运动位置，实际播放与三个历史页启动通过。CPU 对照使用实际 GPU 去彩边后的源缓冲，隔离验证本次采样改动，不将其误称为重新验证全部去彩边逻辑。

另用 48 px TikTok 图标的 2× 放大检查相同高质量采样核中的去彩边前后，源区域与输出均无改动。换用新的色度采样核则会改变图标边缘，两项对照不可混淆。既有小尺寸 VLC 等去彩边误伤和照片精度边界未在本次解决，详见[优化前独立审查](../work/sampling-lab/sbms-final-audit.md)。本次没有把有限的文字和图标验证扩写成“所有内容无损”。

上述倍率实验旧图的源区域、尺寸和采样相位记录于[旧导出清单](../work/sampling-lab/final-exports/manifest.json)。[旧图生成脚本](../work/sampling-lab/build-readme-comparison.py)逐块验证原像素复制、4× 最近邻细节及 PNG 保存后的像素一致性；新场景图使用上一节单独列出的清单。

## 使用与复现

```powershell
python work/sampling-lab/build-dynamic.py
node work/sampling-lab/verify-sbms-final.cjs
node work/sampling-lab/verify-upscale.cjs
python work/sampling-lab/build-readme-comparison.py
```

动态页默认为“优化前 ↔ 优化后”，停在 2× 的原生 Windows 小字。设置中可切到“SBMS 当前 ↔ 优化版”，或“未去彩边 ↔ 优化版”单独观察去彩边阶段。优化前后使用同一份去彩边后的源图，仅放大色度采样不同。

当前演示缓存静态源图的去彩边结果，预览 FPS 不包括每帧重新处理真实桌面的成本。本文不根据该 FPS 宣称产品性能。

## Reference 与串流边界

物理尺寸等输入准确时，以高 PPI 屏幕作为 reference，映射至低 PPI 屏幕，通常会形成高分辨率源到低分辨率输出的缩小路径。Rounded / Integer 舍入可能把接近的密度变为 1:1，手动模式也可能改变结果。高源分辨率增加应用绘制、纹理与复制负担；且当前产品超过 2 倍缩小仍退回双线性，因此不是 reference 越高越好。

Stream only 在 `mapping.rs` 中跳过本地 Renderer，Sunshine 直接捕获虚拟屏。因此高 PPI 串流副屏确实可能需要放大，但具体发生在编码前还是客户端呈现时，取决于串流设置。仅移植本实验到 SBMS 的本地像素着色器，不会自动改善 Stream only；串流接入位置需另行实现，本次未修改这条链路。
